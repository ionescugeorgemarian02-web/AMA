# F4.8 Ecranul „Creierul de brand”

- **Pasul:** F4.8, faza 4.
- **Context:** `docs/18` §18.1 (principii: întâi telefonul, randare pe server), §18.2 (ecranul 6), §18.5 (roluri), `docs/10` §10.4–10.5 (versiuni, aprobare, diferență), ADR-13 (interfață
  randată pe server, întâi pentru telefon). Există depozitul versionat cu `lista`, `istoric`, `diferenta_versiuni`, `aproba`, `retrage` (F4.1), ecranul de fapte (F4.6), onboardingul (F4.4–F4.5) și Campaniile (F4.11).
- **Hotărâri de proiectare.**
  1. *Patru pagini, toate carduri și formulare, fără tabele* (nimic care să forțeze derularea orizontală): `/creier/client` (lista clienților, din meniu), `/creier/client/{id}` (compartimentele, propunerile în așteptare, sursele, faptele,
     pașii de pregătire), `/creier/client/{id}/{compartiment}` (intrările cu versiunea aprobată și propunerile) și `/creier/intrare/{id}` (versiunea aprobată, propunerile, ciornele, diferența, istoricul,
     editarea).
  2. *Editarea creează o propunere nouă* (`creier.propune_schimbare`, sursă „om”, motiv): formularul se construiește din conținutul versiunii aprobate (text, o listă cu un element pe rând, JSON pentru
     structuri), iar un câmp absent din cerere păstrează valoarea veche. Serviciul aplică schema compartimentului și **poarta** (brief complet, strategie completă, brief de insight cu trimiteri, profil de public cu
     citate); o editare care le încalcă nu se salvează și arată problemele. Versiunea aprobată rămâne în vigoare până la aprobarea celei noi.
  3. *Aprobare, respingere (motiv obligatoriu), retragere (motiv obligatoriu), trimiterea unei ciorne spre aprobare* — prin serviciul Creierului (audit în aceeași tranzacție, cu omul). Aprobarea, respingerea și
     retragerea cer `creier.editeaza` (proprietar); editarea și trimiterea unei ciorne cer `creier.editeaza` sau `onboarding.completeaza` (operatorul propune, nu decide); analistul doar citește. CSRF pe tot.
  4. *Diferența între versiuni*: implicit versiunea aprobată față de ultima propunere; oricare două cu `?a=&b=` (formular cu două liste). Se afișează calea, felul (adăugat / scos / schimbat), valoarea de dinainte și de după.
  5. *Faptele și ofertele nu se dublează*: compartimentul „Registru de fapte” trimite la `/creier/fapte?client=` (aprobare cu sursa și citatul exact); „Catalog de oferte” se vede, dar nu se editează aici (are circuitul lui,
     legat de fapte valabile, F4.6). `GET /creier/fapte?client=<id>` filtrează acum pe client (parametrul exista).
  6. *Sursele* (nume, tip, statut, adresă, „doar pentru analiză” unde textul nu se reutilizează), concurenții (formular), și **pașii de pregătire** (ton, citate, public, afirmațiile concurenței, insight, strategie) ca butoane care
     pornesc fluxurile durabile existente (CSRF, `onboarding.completeaza`).
  7. *Pe telefon*: pagina de client are un singur flux vertical; formularele au etichete, câmpuri pe toată lățimea, butoane de cel puțin 44 px (din tema existentă), nicio tabelă, niciun stil sau script inline (CSP strict).
- **Ce se construiește.** `app/panou/creier_ecran_web.py` + patru șabloane, `creier.rezumat_pe_compartimente` și `creier.propuneri_in_asteptare`, intrări de meniu, înregistrarea schemelor și porților la importul ecranului.
- **Ce nu se construiește.** Export (18.2 „exporți”: propunere), editor vizual pentru structuri adânci (JSON în textarea), aprobarea de către client în portal (F7), căutarea în conținut.
- **Contracte de date.** Fără tabele noi. API nou în `creier`: `rezumat_pe_compartimente(db, tenant_id) -> {Compartiment: RezumatCompartiment(intrari, aprobate, in_asteptare, ciorne)}`,
  `propuneri_in_asteptare(db, tenant_id, compartiment=None) -> [(IntrareCreier, VersiuneCreier)]`.
- **Teste de acceptare.** `tests/integration/test_creier_ecran.py`: **fluxul HTTP complet — editezi (propunere nouă), vezi diferența, aprobi, respingi cu motiv, retragi — cu CSRF, permisiuni și audit**; o editare care încalcă poarta nu se
  salvează; pașii și concurenții din ecran; **toate paginile sunt utilizabile la lățime mică** (fără `<table>`, cu `viewport`, fără stiluri sau scripturi inline). Verificare suplimentară, manuală, cu Chrome headless: șase pagini (client, compartiment, intrare, onboarding, campanii, meniu) încărcate într-un `iframe` de 390 px; în toate `scrollWidth` = `clientWidth` (nicio derulare orizontală); capturile sunt în scratchpad-ul sesiunii, nu în repo.
- **NEVERIFICAT / SIMULAT.** Ecranul nu a fost văzut pe un telefon real; verificarea la 390 px s-a făcut cu Chrome headless (vezi STARE). Editarea structurilor adânci ca JSON într-un `<textarea>` pe telefon nu a fost încercată de un om.
- **Riscuri.** RT2 (izolare): clientul se ia din lista RLS a sesiunii, fiecare intrare se citește prin sesiunea cu RLS; RT1: nimic neaprobat nu intră în context (editarea nu aprobă).
- **Module atinse.** `app/panou`, `app/creier` (două funcții de citire), șabloane, teste.
- **Depinde de** F4.1, F4.4–F4.7, F4.9–F4.11. **Deblochează** poarta F4.
- **Revizuire obligatorie:** nu.
- **Întrebări deschise.** Editorul pentru structuri adânci pe telefon; exportul Creierului; cine aprobă din partea clientului.
